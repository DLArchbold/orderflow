● Here is ci.yml (.github/workflows/ci.yml) line by line.

  Header

  - Line 1, name: ci: the workflow's display name. It's what you see in the
    Actions tab sidebar and what gh run list shows.
  - Line 2, on: [push, pull_request]: the triggers. The workflow runs on every
    push to any branch, and on every pull request opened or updated. So your
    push to main triggered it.
  - Line 3, jobs:: the list of jobs. Jobs run in parallel by default, each on
    its own fresh machine. Here backend and frontend run side by side and don't
    depend on each other.

  Backend job (lines 4-11)

  - Line 4, backend:: the job's ID and display name.
  - Line 5, runs-on: ubuntu-latest: the runner is a GitHub-hosted Linux virtual
    machine, wiped after the job.
  - Line 6, steps:: the ordered list of things the job does. If one step fails,
    the later steps are skipped and the job fails.
  - Line 7, uses: actions/checkout@v4: clones your repository onto the runner.
    Without it the machine has no code. @v4 pins the version of this prebuilt
    action.
  - Line 8, uses: actions/setup-java@v4: installs a JDK on the runner.
  - Line 9, with: { distribution: temurin, java-version: '21', cache: maven }:
    the settings for that action.
    - distribution: temurin selects the Eclipse Temurin JDK build.
    - java-version: '21' matches the Java 21 the project requires.
    - cache: maven saves the Maven dependency folder between runs, so later runs
      skip most downloads and finish faster.
  - Line 10, run: mvn -B package: runs a shell command.
    - package compiles the code, runs the tests, and builds the jar.
    - -B is batch mode, which turns off the colored output and download progress
      bars that clutter CI logs.
    - If a test fails or the code doesn't compile, this step and the whole job
      go red.
  - Line 11, working-directory: services/order-service: runs line 10's command
    in that folder. The pom.xml is there, not at the repo root.

  Frontend job (lines 12-21)

  - Lines 12-15: same pattern as the backend. It's a separate job on its own
    fresh Linux machine, and it checks out the code again because jobs don't
    share files.
  - Line 16, uses: actions/setup-node@v4: installs Node.js.
  - Line 17, with: { node-version: '22' }: uses Node 22, matching your local
    version.
  - Lines 18-19, run: npm install in frontend: installs the frontend
    dependencies from package.json.
  - Lines 20-21, run: npm run build in frontend: runs the build script in
    package.json. For a Vite/TypeScript app that normally type-checks and
    bundles, so type errors fail the job.

  Notes on how this affects you
  - This workflow has no Postgres service. If any backend test needs a database,
    mvn package will fail in CI even though it passes locally. A plain unit
    test such as OrderTest is fine.
  - The workflow doesn't cache npm, and npm install can change the lock file.
    npm ci with cache: npm on setup-node is the more reproducible CI choice.
    It's optional.
  - Both jobs must be green for the step 10 check, and GitHub shows each one
    separately on the run page.

> Why is GitHub Actions and ci.yml even needed at all? What is the purpose?

● CI (continuous integration) automatically builds and tests your code on a
  clean machine every time you push. GitHub Actions is GitHub's service for
  running it, and ci.yml (.github/workflows/ci.yml) is the file that tells it
  what to run.

  What it gives you

  - A check that doesn't depend on your machine. Your laptop has your installed
    tools, your local Postgres, and files that might not be committed. CI starts
    from a blank Linux machine and uses only what's in the repo. If it's green,
    the project builds from a fresh clone. This is the real test of the plan's
    "a stranger could follow the README" goal.
  - Early warning on breakage. If you push a compile error, a failing test, or a
    frontend type error, you find out within minutes. You also get a clear
    record of which commit broke it.
  - A guard on pull requests. On a team, a PR shows a red or green check, so
    reviewers know it builds before reading the code. Many teams block merging
    until it's green.
  - Proof for your project. A green badge or check on your repo shows that the
    project builds and tests pass. A recruiter who opens the repo can see that
    at a glance.
  - A foundation for later steps. Phase 2 step 22 extends this same file to
    build Docker images, run integration tests, and scan for vulnerabilities,
    and step 23 uses it to test on Kubernetes.

  Is it required?

  No. The app runs fine without it. Your plan requires it because step 10's
  "Done when" lists a green CI check. For a personal project, it mostly matters
  as a quality signal and as practice with a skill employers expect.

  What this particular file covers

  It only checks that the backend builds and its tests pass, and that the
  frontend builds. It doesn't deploy anything or test against a real database.
