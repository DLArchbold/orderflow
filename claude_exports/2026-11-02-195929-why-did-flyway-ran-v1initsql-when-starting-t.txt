> Why did Flyway ran V1__init.sql when starting the spring boot project in
  services/order-service with mvn spring-boot:run?

● Flyway ran V1__init.sql because of Spring Boot auto-configuration. You didn't
  have to configure anything.

  1. Flyway is on the classpath. pom.xml:22-23
     (services/order-service/pom.xml#L22-L23) declares flyway-core and
     flyway-database-postgresql.
  2. Spring Boot's FlywayAutoConfiguration switches on by default. It activates
     when Flyway is on the classpath and a DataSource exists.
     spring.flyway.enabled defaults to true, and application.yml
     (services/order-service/src/main/resources/application.yml) never sets it
     to false.
  3. It uses your datasource. The settings in spring.datasource
     (jdbc:postgresql://localhost:5432/orders) tell Flyway which database to
     connect to.
  4. It scans the default migration location. That location is
     classpath:db/migration, and V1__init.sql
     (services/order-service/src/main/resources/db/migration/V1__init.sql) sits
     there. The V<version>__<description>.sql filename is what Flyway looks for.
  5. The migration runs before JPA starts. Spring Boot makes the
     EntityManagerFactory depend on Flyway. On startup Flyway checks its
     flyway_schema_history table. If it doesn't exist or V1 isn't recorded,
     Flyway runs V1__init.sql and records it.

  The ordering matters because of ddl-auto: validate (application.yml:12
  (services/order-service/src/main/resources/application.yml#L12)). Hibernate
  only checks that the tables match your entities. Flyway has to create them
  first.

  You'll see it run on the first start against a fresh orders database. Later
  starts skip V1, because Flyway sees it's already applied and only checks its
  checksum. If you edit V1 after it has run, startup fails with a checksum
  mismatch.

  To turn this off, set spring.flyway.enabled: false. To change the scripts'
  location, set spring.flyway.locations.

> How do enums work in Java and how does the allowedNext() method function?

  Read 1 file (ctrl+o to expand)

● How Java enums work

  An enum is a special class with a fixed set of instances. PENDING, CONFIRMED,
  REJECTED, CANCELLED are the only four OrderStatus objects that will ever
  exist.

  - Each constant is a public static final instance of the enum, created once
    when the class loads.
  - You can't call new OrderStatus(). The constructor is implicitly private.
  - Because there is exactly one instance of each constant, you can compare them
    with ==.
  - An enum is a full class. It can have fields, constructors and methods, and
    it can implement interfaces. allowedNext() is one of those methods.
  - The compiler gives you values(), valueOf(String), name() and ordinal().
    Order uses this when it prints status in its error message.
  - The semicolon on line 6 is required because members follow the constants.

  How allowedNext() works

  OrderStatus.java:8-14 (services/order-service/src/main/java/com/orderflow/orde
  r/domain/OrderStatus.java#L8-L14) is a state machine written as a switch
  expression on this. this is whichever constant the method was called on.

  ┌─────────────────────┬────────────────────────────────┐
  │   Current status    │          Allowed next          │
  ├─────────────────────┼────────────────────────────────┤
  │ PENDING             │ CONFIRMED, REJECTED, CANCELLED │
  ├─────────────────────┼────────────────────────────────┤
  │ CONFIRMED           │ CANCELLED                      │
  ├─────────────────────┼────────────────────────────────┤
  │ REJECTED, CANCELLED │ none (Set.of())                │
  └─────────────────────┴────────────────────────────────┘

  - -> arms don't fall through, so no break is needed.
  - return switch: the switch is an expression that produces a value.
  - No default is needed, because the compiler knows every enum constant is
    covered. If you add a new constant like SHIPPED and forget to handle it
    here, this stops compiling. That's the main advantage over a default branch.
  - Set.of(...) returns an immutable set, so callers can't change the rules.
    Set.of() is an empty set, which marks REJECTED and CANCELLED as terminal
    states.

  How Order uses it

  Order.transitionTo() (Order.java:33-38 (services/order-service/src/main/java/c
  om/orderflow/order/domain/Order.java#L33-L38)) calls
  status.allowedNext().contains(next). If the target isn't allowed, it throws
  IllegalStateException. So reject() on a CONFIRMED order fails, and nothing can
  leave a terminal state.

> Is this the way to represent one-to-many relationships between tables in
  JPA/Hibernate?
  @ElementCollection
      @CollectionTable(name = "order_lines", joinColumns = @JoinColumn(name =
  "order_id"))
      @OrderColumn(name = "line_no")
      private List<OrderLineEmbeddable> lines = new ArrayList<>();

● It's one way, and it fits this case. The usual way is @OneToMany with a
  separate @Entity.

  Two ways to map one-to-many

  @OneToMany / @ManyToOne is the standard way. The child is a full entity with
  its own @Id, and the two sides are linked as entities:

  @OneToMany(mappedBy = "order", cascade = ALL, orphanRemoval = true)
  private List<OrderLineEntity> lines;      // child has @ManyToOne OrderEntity
  order

  Use it when the child has its own identity or lifecycle. Examples are querying
  children directly, referencing them from other tables, or giving them their
  own relationships.

  @ElementCollection is what you pasted. The child is a value type
  (@Embeddable), not an entity. It has no id and no repository, and it exists
  only as part of its parent. Hibernate always loads, saves and deletes the
  children through the parent.

  Why @ElementCollection suits order_lines

  - The table's primary key is (order_id, line_no), so a line has no identity
    apart from its order and position.
  - A line is just sku and quantity. Nothing else points at it.
  - You never need to fetch or save a line on its own.
  - It needs fewer classes and no two-way order / lines bookkeeping.

  Trade-off

  Hibernate handles changes to an element collection coarsely. Changing a list
  that has no @OrderColumn makes Hibernate delete all the child rows and
  re-insert them. With @OrderColumn it can do smaller updates, but inserting or
  removing in the middle still shifts indexes. That doesn't matter here, because
  order lines are written once and rarely edited.

  If lines later get their own id, status or relationships (for example a
  per-line shipment), switch to @OneToMany with an OrderLineEntity. Your schema
  would need a surrogate key for that.

> What are the needed changes if I want OrderLine to be an Entity as well?

● Three things change: the schema, the new child entity, and the parent's
  mapping.

  1. Schema: add V2__order_lines_id.sql

  An entity needs its own @Id, and order_lines currently has only the composite
  key (order_id, line_no). The simplest fix is a surrogate key. Don't edit
  V1__init.sql. Flyway has already applied it, so changing it causes a checksum
  mismatch. Add a new migration instead:

  ALTER TABLE order_lines DROP CONSTRAINT order_lines_pkey;
  ALTER TABLE order_lines ADD COLUMN id BIGINT GENERATED ALWAYS AS IDENTITY
  PRIMARY KEY;
  ALTER TABLE order_lines ADD CONSTRAINT uq_order_lines_order_line UNIQUE
  (order_id, line_no);

  Existing rows get ids automatically, and the unique constraint keeps one
  line_no per order.

  The plan's step 12 uses phase2/order-service/V2__idempotency_and_outbox.sql.
  This new file takes version 2, so that one has to be renamed to V3__... when
  you get there.

  2. New OrderLineEntity, replacing the @Embeddable

  @Table(name = "order_lines")
  public class OrderLineEntity {

      private Long id;

      @JoinColumn(name = "order_id")
      private OrderEntity order;

      @Column(name = "line_no", nullable = false) private int lineNo;
      @Column(nullable = false) private String sku;
      @Column(nullable = false) private int quantity;

      protected OrderLineEntity() {}
      OrderLineEntity(OrderEntity order, int lineNo, String sku, int quantity) {
  ... }
      // getters
  }

  GenerationType.IDENTITY matches the GENERATED ALWAYS AS IDENTITY column.
  Delete OrderLineEmbeddable.

  3. OrderEntity: swap the mapping

  Replace @ElementCollection, @CollectionTable and @OrderColumn with:

  @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval =
  true)
  @OrderBy("lineNo ASC")
  private List<OrderLineEntity> lines = new ArrayList<>();

  public void addLine(String sku, int quantity) {
      lines.add(new OrderLineEntity(this, lines.size(), sku, quantity));
  }

  - mappedBy = "order": the child owns the foreign key through its @ManyToOne,
    so the parent doesn't write the join column.
  - cascade = ALL: saving the order saves its lines, and deleting the order
    deletes them.
  - orphanRemoval = true: a line removed from the list is deleted from the
    table.
  - @OrderBy("lineNo ASC"): replaces @OrderColumn. lineNo is now an ordinary
    field you set yourself. @OrderColumn would also work with mappedBy, but it
    is easy to get wrong. Setting lineNo in addLine is more explicit.
  - Both sides are set: the helper makes sure the child's order reference is
    filled. If it is null, the insert fails on order_id NOT NULL.

  Things to watch

  - Repository: you still only need JpaRepository<OrderEntity, UUID>. Add an
    OrderLineRepository only if you query lines on their own.
  - N+1 queries: listing orders and then reading lines runs one extra query per
    order. Use @EntityGraph(attributePaths = "lines") or a join fetch query on
    the list endpoint.
  - equals / hashCode: if you put lines in a Set or compare them, base equality
    on the id or a business key, not on the default object identity.

  Why it exists

  It sits between the database model and the HTTP response. The controller
  methods return it (ResponseEntity<OrderResponse> in OrderController.java
  (services/order-service/src/main/java/com/orderflow/order/web/OrderController.
  java)), and the response body is its JSON form.

  You could return OrderEntity directly instead, but that would be a mistake:

  - The API contract becomes tied to the table mapping. Renaming a column or
    field would silently change the public JSON. With a DTO, the response shape
    changes only when you change it.
  - Lazy loading breaks serialization. OrderEntity.lines is lazy. Jackson would
    touch it after the transaction ends (open-in-view: false in application.yml
    (services/order-service/src/main/resources/application.yml)) and throw
    LazyInitializationException.
  - Internal fields leak. The response would include createdAt, updatedAt and
    any future internal fields, and the entity's back-reference from line to
    order would cause infinite recursion.
  - Swagger. springdoc builds its schema from this record, so the docs show a
    clean, intentional shape. Step 6 adds @Schema(example = ...) to it.

  The same reasoning is behind CreateOrderRequest. Input and output are separate
  types, because a client shouldn't be able to send an id or status, and the
  response needs to include them.

  property names:

  Reason: Echoes who the order belongs to. It is TEXT in the schema.

  Component: String status

> What does instnatiating an OrderRepository field in OrderService and

● It doesn't instantiate anything. The field private final OrderRepository
  orders; only declares a reference, and the constructor assigns an object that
  Spring created.

  What happens at startup

  1. OrderRepository is only an interface. Spring Data JPA sees OrderRepository
     extends JpaRepository<...> and generates a proxy class that implements it
     (save, findById, findAll and so on). It registers that object as a bean.
  2. @Service makes OrderService a bean too. Spring has to build it by calling
     its constructor.
  3. Spring sees the constructor needs an OrderRepository. It looks up the
     repository bean and passes it in. This is constructor injection, a form of
     dependency injection.
  4. The constructor stores that object in orders. Every service method then
     calls the same repository bean.

  Since the class has a single constructor, you don't need @Autowired.

  Why do it this way

  - Spring owns the lifecycle. The repository needs a DataSource, an
    EntityManager and transaction wiring. You couldn't new it yourself, and you
    wouldn't want to.
  - final means it can't be reassigned or left null. If the dependency is
    missing, the app fails at startup and not with a NullPointerException on the
    first request.
  - Testing is easier. In a unit test you can call new
    OrderService(fakeRepository) with a mock, with no Spring involved. Field
    injection with @Autowired makes that harder.
  - One shared instance. The service and repository are singletons, so all
    requests share them. That is safe because they hold no per-request state.

  The same pattern applies when you add OrderService to OrderController. Put a
  private final OrderService service; field there and take it as a constructor
  parameter.

● OrderRepository

  OrderRepository.java (services/order-service/src/main/java/com/orderflow/order
  /persistence/OrderRepository.java) is the data access layer. It is one line:

  public interface OrderRepository extends JpaRepository<OrderEntity, UUID> {}

  Extending JpaRepository<OrderEntity, UUID> (entity type, id type) gives you
  save, findById, findAll, deleteById, count, paging and more, without writing
  any SQL or implementation. You can add methods like findByCustomerId(String
  id), and Spring Data derives the query from the name.

  It's important because it's the only place the rest of the app talks to the
  database. OrderService says "save this order" and doesn't know about
  connections, SQL or Hibernate sessions.

  What a bean is

  A bean is an object that the Spring container creates, configures and manages,
  as opposed to one you create with new. The container is called the
  ApplicationContext. Beans are singletons by default, so there is one shared
  instance.

  Being a bean gives an object things a plain object doesn't get:
  - Spring builds it and supplies its dependencies.
  - Spring can wrap it in a proxy to add behavior. @Transactional works this
    way: the proxy opens a transaction before your method runs and commits or
    rolls back after.
  - Its lifecycle (startup, shutdown) is managed.

  How Spring ties it together

  At startup Spring does roughly this:

  1. Scans for components. @SpringBootApplication on OrderServiceApplication
     includes component scanning of com.orderflow.order and everything below it.
  2. Registers beans. It finds @Service, @RestController, @RestControllerAdvice,
     @Configuration and similar classes. Spring Data JPA also finds the
     OrderRepository interface and generates an implementation for it.
  3. Wires dependencies. For each bean's constructor, it finds beans of the
     needed types and passes them in. The chain here is OrderController →
     OrderService → OrderRepository → EntityManager → DataSource.
  4. Starts the app. HTTP requests then reach the controller bean, which calls
     the service bean, which calls the repository bean.

  This is inversion of control. Your classes declare what they need, and the
  framework decides how to build and connect everything.

  Why OrderService must be a bean

  - @Transactional only works on beans. Spring implements it with a proxy around
    the bean. If you wrote new OrderService(repo), no proxy would exist, and
    confirm() would run with no transaction. Dirty checking wouldn't save the
    status change, and lazy lines couldn't be loaded.
  - The controller can't get it otherwise. OrderController is built by Spring,
    so it receives an OrderService from the container. If you called new, you'd
    have to build the repository by hand, which isn't possible.
  - One shared instance is used across requests, and it's easy to swap for a
    mock in tests.

  What to add so a class can be injected

  You need two things.

  1. Mark it for Spring with a stereotype annotation on the class, in a package
  under the application class:

  ┌─────────────────────────────┬───────────────────────────────────────────┐
  │         Annotation          │                  Use for                  │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ @Service                    │ business logic, such as OrderService      │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ @Repository                 │ data access (already implied for Spring   │
  │                             │ Data interfaces)                          │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ @RestController             │ web endpoints                             │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ @Component                  │ anything else                             │
  ├─────────────────────────────┼───────────────────────────────────────────┤
  │ @Configuration with @Bean   │ objects you can't annotate, such as       │
  │ methods                     │ third-party classes                       │
  └─────────────────────────────┴───────────────────────────────────────────┘

  2. Ask for it by declaring a constructor parameter in the class that needs it:

  private final OrderService service;
  public OrderController(OrderService service) { this.service = service; }

  With one constructor, @Autowired isn't needed.

  The common mistakes are forgetting the annotation (startup fails with No
  qualifying bean of type ...), putting the class outside the scanned packages,
  or calling new on a bean. In the last case you get a plain object with no
  injection and no transactions.

  Also, what does @Transactional do?
● What @Transactional does

  A database transaction groups several operations into one all-or-nothing unit.
  @Transactional on a method (or a class) tells Spring: open a transaction
  before this method, run it, then commit if it returns normally or roll back if
  it throws a RuntimeException.

  In JPA terms there's a second effect. The transaction also opens a persistence
  context (Hibernate's Session) that lives until the method ends. Entities
  loaded inside it are managed, and Hibernate tracks them.

  How a proxy makes it work

  Your OrderService code has no transaction logic in it. Spring adds that by
  wrapping the bean. The controller isn't given your OrderService object. It's
  given a generated subclass (the proxy) that holds your real object inside it.

  OrderController ──calls──▶ [Proxy] ──▶ real OrderService.confirm()
                              │ 1. begin transaction
                              │ 2. call the real method
                              │ 3. commit (or roll back on exception)

  Roughly, the proxy does this:

  tx = txManager.begin();
  try { result = realService.confirm(id); txManager.commit(tx); return result; }
  catch (RuntimeException e) { txManager.rollback(tx); throw e; }

  Only Spring can build this wrapper, and only for beans it creates. If you
  write new OrderService(repo), you get the bare class with no wrapper, so the
  annotation is just text that nothing reads. The same applies when a method
  inside the class calls another @Transactional method of the same class. That
  call goes straight to the real object and skips the proxy, so the annotation
  is ignored there.

  What breaks in confirm() with no transaction

  OrderEntity order = find(id);   // repository loads it
  order.confirm();                // changes status in memory
  return OrderResponse.from(order);

  The repository's own methods are transactional, so with no service-level
  transaction findById runs in its own short transaction. It then commits and
  closes the session before returning. That causes two problems:

  1. The status change is never saved. The entity is now detached, so nobody is
     tracking it. order.confirm() changes only the Java object. Dirty checking
     happens at commit by comparing a managed entity with its loaded snapshot,
     and that commit has already happened. You'd return CONFIRMED in the JSON
     while the row in Postgres still says PENDING.
  2. Lazy loading fails. lines is a lazy collection, loaded on first access and
     only while the session is open. After the session closes,
     OrderResponse.from calling getLines() throws LazyInitializationException.
     With open-in-view: false in application.yml
     (services/order-service/src/main/resources/application.yml), nothing keeps
     a session open for you.

  With @Transactional on the service, the session stays open for the whole
  confirm() call. find returns a managed entity, confirm() changes it, from()
  can load the lines, and at commit Hibernate sees the status difference and
  issues the UPDATE. That's why there's no save call.

  Other details

  - Atomicity. create writes one orders row and several order_lines rows. If an
    insert fails halfway, the rollback undoes all of them.
  - Rollback rules. By default only unchecked exceptions (RuntimeException,
    Error) roll back. This is why IllegalStateException from an illegal
    transition aborts the transaction.
  - readOnly = true on list and get is a hint. Hibernate skips dirty checking
    and can use cheaper settings, and Postgres can treat the transaction as
    read-only.
  - Which annotation. Spring's
    org.springframework.transaction.annotation.Transactional has readOnly,
    propagation and rollbackFor. The Jakarta one doesn't have readOnly. That's
    why I switched it in the service.

> Can you elaborate more on this part?
  "Dirty checking happens at commit by comparing a managed entity with its
  loaded snapshot, and that commit has already happened. You'd return CONFIRMED
  in the JSON while the row in Postgres still says PENDING."

● What dirty checking is

  Hibernate doesn't watch your fields as you change them. It works by
  comparison, in three steps.

  1. Snapshot on load. When an entity is loaded inside a session (the
  persistence context), Hibernate keeps two things: the entity object you get,
  and a hidden copy of its column values at load time.

  persistence context
    OrderEntity@abc  (the live object you modify)
    snapshot of abc:  status=PENDING, updatedAt=10:00:00, customerId=c1, ...

  2. You change the object. order.confirm() runs status = CONFIRMED; updatedAt =
  Instant.now(). These are plain Java field assignments, and Hibernate isn't
  notified. Only the live object differs from the snapshot now.

  3. Compare at flush. Hibernate flushes at commit (and sometimes before a
  query). It walks every managed entity and compares current values with the
  snapshot. For each entity that differs, it queues an UPDATE, here:

  UPDATE orders SET customer_id=?, status='CONFIRMED', created_at=?,
  updated_at=? WHERE id=?

  By default it writes all columns, not just the changed ones. @DynamicUpdate
  would change that. Then the SQL runs and the transaction commits. This is why
  confirm() has no save() call. The entity is managed, so the change is detected
  on its own.

  The timeline with @Transactional

  begin tx ─ find(id) ─ confirm() ─ OrderResponse.from() ─ [flush: compare →
  UPDATE] ─ commit
             │ snapshot taken       │ live object changed
        │
             └──────────────── session open the whole time
  ──────────────────────────────┘

  The timeline without it

  find(id):   begin tx ─ SELECT ─ commit, session closed      ← repository's own
  tiny transaction
  confirm():  live object changed to CONFIRMED                 ← session already
  gone
  from():     builds JSON from the live object → "CONFIRMED"
  (end)       nothing compares anything, no UPDATE is issued

  The sentence I wrote means two things:

  - "That commit has already happened": the only flush opportunity was at the
    end of find's transaction, which came before you changed anything. So
    Hibernate compared an unchanged entity and found nothing to update.
  - "You'd return CONFIRMED… while the row says PENDING": the JSON is built from
    the in-memory object, which says CONFIRMED. Postgres was never told, so a
    later GET would return PENDING. Nothing throws an exception, so this bug is
    silent.

  After the session closes, the entity is detached. It's a plain Java object
  that Hibernate no longer tracks. The lines lazy-loading failure comes from the
  same closed session.

  Related points

  - An explicit save() would fix the status bug without a transaction. On a
    detached entity it does a merge, which copies the state into a fresh managed
    copy and updates the row in its own transaction. But you'd still have the
    lazy-loading problem, and operations that need to be atomic (like create
    with its lines) would no longer be.
  - Entities created with new are not tracked until saved. In create,
    orders.save(order) is what makes Hibernate track the new entity, and it
    issues the INSERT.
  - readOnly = true tells Hibernate to skip this snapshot comparison, which is a
    small saving on list and get.
  - The change must happen inside the session. Modifying an entity from a
    request thread after the service method returns has no effect on the
    database, for the same reason.

> What does @EntityGraph do?

● @EntityGraph tells JPA which associations to load together with an entity, for
  one specific query. It overrides the fetch strategy you set on the mapping,
  for that query only.

  The problem it solves

  OrderEntity.lines is a @OneToMany, which is lazy by default. Hibernate doesn't
  load the lines with the order. It loads them the first time you call
  getLines().

  Without the annotation, list() would do this:

  SELECT * FROM orders                          -- 1 query for N orders
  SELECT * FROM order_lines WHERE order_id = ?  -- once per order, when
  OrderResponse.from() touches getLines()
  SELECT * FROM order_lines WHERE order_id = ?
  ... N times

  That's the N+1 problem: 1 query plus N more, so 100 orders cost 101 round
  trips.

  What it does here

  @EntityGraph(attributePaths = "lines")
  List<OrderEntity> findAll();

  attributePaths = "lines" names the association (the field lines on
  OrderEntity) to load eagerly for this method. Hibernate adds a join and
  fetches everything in one query:

  SELECT o.*, l.* FROM orders o LEFT JOIN order_lines l ON l.order_id = o.id

  Hibernate then builds each OrderEntity once and fills its lines from the
  joined rows. You still have lines as lazy on the entity, so other methods like
  findById are unaffected. Only findAll() pays for the join.

  Why use it rather than other options

  - fetch = FetchType.EAGER on the mapping would load lines for every query,
    even when you don't need them.
  - A custom @Query("select o from OrderEntity o join fetch o.lines") gives the
    same result, but you write the JPQL yourself. @EntityGraph is shorter and
    works with derived methods like findAllByOrderByCreatedAtDesc().
  - @Override is needed because findAll() already exists on JpaRepository.
    You're replacing its default behavior with the graph attached.

  Limitations

  - It loads all the lines for every order. For a large table you'd paginate,
    and paging with a collection join is awkward because Hibernate can end up
    paginating in memory.
  - You can list several paths (attributePaths = {"lines", "other"}), but
    fetching more than one collection in a single join can multiply rows.
    Hibernate may reject a fetch of two List collections with a
    MultipleBagFetchException.
  - @EntityGraph also supports nested paths like "lines.product", for entities
    reached through the association.
