  OutboxLagHigh, "Pending" and "Firing"

  - Outbox lag: order-service writes the order and an "OrderCreated" event row
    to its outbox table in one transaction. A publisher then sends unpublished
    rows to Kafka. The lag is how old the oldest unpublished row is. Normally
    it's about 0 s. With Kafka stopped, rows can't be sent, so the lag grows by
    1 s every second.
  - OutboxLagHigh: a Prometheus alert rule, orderflow_outbox_lag_seconds > 60
    for 2 minutes. It means events have been stuck for over a minute and that
    has lasted 2 minutes.
  - Pending: the condition is true but hasn't yet lasted the required 2 minutes.
  - Firing: it has been true for 2 minutes without a break, so the alert is
    active.
  - "+88 s" and "+208 s": seconds after I stopped Kafka. The lag crossed 60 s at
    +63 s, and Pending began at +88 s. Firing began at +208 s, exactly 2
    minutes later.
  - "Accounted for": that comes from drill_check.py, which compares what the
    client was told with what the database holds:
    - the load tool received 3,600 201 responses;
    - the orders table has 3,600 new rows;
    - all 3,600 reached CONFIRMED, with none stuck PENDING;
    - 0 outbox rows are left unpublished in either service;
    - no order has duplicate events;
    - the reserved stock per SKU matches the confirmed quantities exactly.

    So every order the API acknowledged was delivered and processed exactly
    once.

  "Failed" versus "lost"

  They are not the same, and neither means "committed but not published".

  - Failed request: the load tool got no 201 back. In load_orders.py a failure
    is a non-2xx HTTP status or an exception, which is recorded as status 0. The
    21 failures at 600/s were all status 0, meaning the client waited 10 s (its
    timeout) or the connection broke. The service was overloaded and answered
    too slowly. The slowest request in that run took 10.03 s, which fits the 10
    s timeout. I haven't traced why those 21 requests timed out, so overload is
    my inference. I also can't say whether the server created an order for any
    of them, because the client never learned the result.
  - Lost: an order the client got a 201 for that isn't in the database, or that
    stayed PENDING forever. The drill checks guard that definition.
  - Committed but not published: that's the outbox's job. Those rows wait and
    get sent when Kafka returns. The "0 unpublished outbox rows" check confirms
    none were left behind after draining.

  So "0 failed at 400/s" means every request got a timely 201. "0 lost in the
  drills" means every acknowledged order ended up processed. The
  order-service-kill drill had 600 failed requests because the API was down, and
  those were never acknowledged, so they don't count as lost.

    dead, so they got "connection refused".

    time the restart separately.

  held 129,679 rows, which is the 126,679 baseline plus exactly the 3,000
