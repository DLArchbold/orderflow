  3. Create an order

  Create an order through the UI. Pick items that exist in inventory. The
  inventory service rejects stock it can't reserve, and that ends in REJECTED,
  not CONFIRMED.

  4. Check the status

  The order starts as PENDING. It should become CONFIRMED within a few seconds,
  if the UI refreshes or you reload:

  1. order-service saves the order and writes an outbox event.
  2. The event goes to Kafka.
  3. inventory-service reserves the stock and publishes RESERVED.
  4. order-service receives that result and confirms the order.

  The status transitions are in OrderStatus.java (services/order-service/src/mai
  n/java/com/orderflow/order/domain/OrderStatus.java).

● This is a browser restriction, not a bug in your deploy. The frontend uses the
  OIDC PKCE flow. It hashes a code challenge with crypto.subtle, and browsers
  only provide that on HTTPS or localhost. Your ALB is plain HTTP on a
  non-localhost hostname, so the call throws before the redirect to Keycloak.

  Keycloak isn't the problem. The realm already has "sslRequired": "none"
  (orderflow-realm.json:4 (phase2/infra/keycloak/orderflow-realm.json#L4)), so
  it accepts HTTP.

  Option A: tell Chrome or Edge to treat the ALB as secure (recommended for a
  smoke test)

  This needs no infrastructure changes and costs nothing.

  1. Open chrome://flags/#unsafely-treat-insecure-origin-as-secure. In Edge, use
     edge://flags/#unsafely-treat-insecure-origin-as-secure.
  2. Enable the flag and enter the origin with no trailing slash:
     http://orderflow-1966634175.us-east-1.elb.amazonaws.com
  3. Click Relaunch.
  4. Reload the app and click Log in.

  The flag applies to that one origin, so remove it afterwards. The ALB hostname
  changes after a destroy and re-apply, so you'd have to update the flag then
  too.

  If it still fails, open DevTools and run window.isSecureContext. It must print
  true.

  Login also needs the Keycloak origin to be secure. Keycloak is on the same ALB
  hostname (/realms/*), so the one flag covers both.

  Option B: real HTTPS on the ALB

  This is the proper fix, but it needs more than the smoke test warrants:

  - You need a domain you own, an ACM certificate and an HTTPS listener on 443.
    ALB hostnames like *.elb.amazonaws.com can't get an ACM certificate.
  - alb_url, the Keycloak issuer, the realm redirect URIs and config.js all have
    to switch to https://. They are built from local.alb_url, so that should be
    one change, but I haven't looked at it in detail.

  Do this only if you want a lasting deployment. Your README already calls this
  stack a throwaway that is public and HTTP-only, so Option A fits.
