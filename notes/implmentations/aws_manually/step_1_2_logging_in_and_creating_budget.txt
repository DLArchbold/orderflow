> Does "terraform plan -var "budget_email=you@example.com"
  -target=aws_budgets_budget.monthly" run any file in the project?

● Not in the sense of running a program. Terraform doesn't execute your files.
  It reads them as configuration.

  What it reads

  - Every .tf file in the current folder: main.tf, variables.tf, network.tf,
    data.tf, alb.tf, ecs_base.tf, ecs_services.tf and outputs.tf. Terraform
    loads them all together, so the file names don't matter. It reads all of
    them even with -target, because it has to build the full dependency graph
    before narrowing to one resource.
  - terraform.tfvars, if present: it's loaded automatically, but you don't have
    one yet.
  - .terraform/ and .terraform.lock.hcl: these are the downloaded providers and
    version pins from terraform init.
  - terraform.tfstate: it records what Terraform has already created. Right now
    it's missing or empty.

  What it does with them

  1. It parses the .tf files and checks they're valid.
  2. It calls the AWS API to read the availability zones data source. This is a
     read-only call.
  3. It compares the budget resource in data.tf:3
     (phase2/infra/terraform/data.tf#L3) with the state. The state has nothing
     yet, so it plans to create it.
  4. It prints the plan. A plan changes nothing in AWS and writes nothing to
     state.

  What it doesn't run

  - It doesn't run your Java, TypeScript or Docker code.
  - It doesn't run scripts, unless a .tf file contains a local-exec provisioner
    or an external data source. I haven't grepped for those. Run Select-String
    -Path *.tf -Pattern "local-exec|external" in the terraform folder to
    confirm. I'd expect no matches.
  - It doesn't touch files outside the terraform folder. The only exception is a
    .tf file that reads one with file() or templatefile(). Run Select-String
    -Path *.tf -Pattern "file\(" to check. The Keycloak realm JSON under
    phase2/infra/keycloak/ is the likely one.

  The -var flag only sets the budget_email variable declared in variables.tf:17
  (phase2/infra/terraform/variables.tf#L17).

  from, and it doesn't search parent or child folders. Run from anywhere else,
  it reports "No configuration files" or a similar error. It also needs the
  .terraform/ folder and terraform.tfstate that init creates in that folder.

  There are two ways to run it from elsewhere:

  # From the repo root, using -chdir

  terraform -chdir=phase2/infra/terraform plan -var
  "budget_email=you@example.com" -target=aws_budgets_budget.monthly

  Use -chdir before the subcommand, and use it on every command. If you run init
  in one folder and plan in another, the second one fails because the providers
  aren't installed there.

  Staying in the folder is simpler and less error-prone:

  cd "C:\Users\WJ\Desktop\Work
  2023-05-12\Project\orderflow\phase2\infra\terraform"

  to run in that folder or use the same -chdir.

> Why don't I need to change AWS_PROFILE and AWS_REGION in
  Microsoft.PowerShell_profile.ps1 after changing permission set for the user?

● You're right that a permission set change alone doesn't require editing either
  variable. My earlier advice to update AWS_PROFILE was only because of a name
  mismatch.

  Why they normally don't change

  - AWS_PROFILE is only a name, a pointer to a [profile ...] block in
    ~/.aws/config. The permission set is a setting inside that block
    (sso_role_name = AdministratorAccess). If you edit the block and keep the
    name, the variable still points to the right place.
  - AWS_REGION is the region the CLI and Terraform call (us-east-1). A
    permission set changes what you're allowed to do. It doesn't change where.

  Why yours needed a fix

  Your variable held AdministratorAccess-702623019395, but the only profile in
  the config is SystemAdministrator-702623019395. That was a mismatch between
  the variable and the config, and it had nothing to do with the permission set.
  You can fix it either way:

  - Change the variable in Microsoft.PowerShell_profile.ps1 to
    SystemAdministrator-702623019395. This keeps the config as it is.
  - Rename the profile block in ~/.aws/config to
    AdministratorAccess-702623019395, and leave the variable alone.

  Either way, a new terminal needs to be able to resolve the variable to an
  existing profile. A quick test in a fresh terminal is aws configure
  list-profiles, then $env:AWS_PROFILE. The value you see should appear in the
  list.

  You also still need aws sso login after the permission change, because your
  cached session is for the old role.
