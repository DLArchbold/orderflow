● Your setup is PostgreSQL with two databases, orders and inventory. Locally
  they run in docker-compose, and on AWS they run in RDS.

  Local (docker-compose)

  First find the container name and the DB user. Check docker-compose.yml if
  either differs from my guesses below.

  docker ps --format "{{.Names}}"
  docker exec -it <postgres-container> psql -U <user> -d orders

  Then, inside psql:

  \dt                                   -- list tables
  SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;   -- column name may
  differ
  SELECT * FROM order_lines;
  SELECT * FROM outbox;                 -- events waiting to be published
  SELECT * FROM idempotency_keys;
  \c inventory                          -- switch database
  SELECT * FROM stock;
  SELECT * FROM reservations;
  SELECT * FROM processed_messages;
  \x                                    -- toggle expanded output for wide rows
  \q

  You can also run a one-off query without opening a session:

  docker exec -it <container> psql -U <user> -d orders -c "SELECT * FROM
  orders;"

  A GUI also works: DBeaver or pgAdmin connected to localhost:5432, if the
  compose file publishes that port.

  On AWS (RDS)

  RDS sits in private subnets and isn't reachable from the internet. It only
  accepts connections from the services' security group and the one-off
  DB-creation task, as set in network.tf. You have three options:

  1. One-off ECS task running psql. This follows the pattern in ecs_base.tf:74,
     which already runs postgres:16 with psql -h <rds_endpoint> -U orderflow.
     Copy that task definition, change the command to something like SELECT *
     FROM orders;, run it, and read the output in CloudWatch Logs. The password
     is in Secrets Manager.
  2. ECS Exec into a running service task. This needs enableExecuteCommand set
     on the service and the SSM permissions on the task role. Then run aws ecs
     execute-command ... --command "/bin/sh". The service images probably don't
     include psql, though.
  3. Port-forward through a bastion or SSM host. This is the most convenient for
     a GUI client, but it means adding an EC2 instance and an ingress rule on
     the RDS security group.

  The simplest is option 1 for occasional checks. Find the endpoint with
  terraform output rds_endpoint.

  I can write a reusable "query" task definition in Terraform, or look up the
  exact container and user names from your compose file, if you want either.

> How can I use PGAdmin to connect to the database?

● Local Postgres (docker-compose)

  Port 5432 is published to your machine, so pgAdmin can connect directly. First
  make sure the container is running: docker ps.

  In pgAdmin:

  1. Right-click Servers → Register → Server…
  2. General tab: Name = orderflow-local (any name).
  3. Connection tab:
     - Host name/address: localhost
     - Port: 5432
     - Maintenance database: orders
     - Username: orderflow
     - Password: orderflow (tick Save password)
  4. Click Save.

  Both databases will appear under the server. Browse a table at Databases →
  orders → Schemas → public → Tables → orders, then right-click it and choose
  View/Edit Data → All Rows. You can also open Tools → Query Tool and run SQL.
  The inventory database is listed next to orders. If it's missing, right-click
  Databases and choose Refresh.

  If the connection fails:
  - Another Postgres installed on Windows may already be using 5432, and pgAdmin
    would then be talking to that one instead. Check with netstat -ano |
    findstr :5432, or change the compose mapping to "5433:5432" and use
    port 5433.
  - If you run pgAdmin itself in Docker, use host.docker.internal as the host
    instead of localhost.

  AWS RDS

  pgAdmin can't reach RDS directly because it's in private subnets. You'd need a
  tunnel, such as an SSM port-forward through a small EC2 host in the VPC. In
  that case:

  - Host: localhost, and Port: the local port you forwarded
  - Username: orderflow
  - Password: from Secrets Manager
  - Under the SSL tab, set SSL mode to require

  The other option is to keep using a one-off ECS psql task, as I described
  before. I can add the bastion/SSM host to the Terraform if you'd like the
  pgAdmin route on AWS.

● This is expected, and it isn't hurting your smoke test.

  What the logs mean

  - The Terraform for AWS has no Redis. Neither ElastiCache nor a Redis
    container is defined in phase2/infra/terraform.
  - order-service still tries to reach Redis, using the default localhost:6379,
    for the GET /api/stock/SKU-1 lookup that the UI makes. The connection fails
    after the 500 ms timeout set in application.yml:17
    (services/order-service/src/main/resources/application.yml#L17).
  - CacheConfig catches the error and logs a WARN for each cache get and put.
    The request then falls through to inventory-service and still returns a
    result. This is the "cache is an optimisation, never a requirement"
    behaviour from step 17c.
  - Readiness checks ignore Redis, set by redis.enabled: false at
    application.yml:89-90
    (services/order-service/src/main/resources/application.yml#L89-L90). So the
    service isn't marked unhealthy.
  - Order creation, CONFIRMED and GET /orders don't touch Redis. That's why your
    smoke test passes.

  Two WARN lines per stock lookup (get and put) is the pattern in your pasted
  logs.

  Your options

  1. Leave it. It's a legitimate demo of graceful degradation, and your plan's
     step 24 already treats skipping Redis on the deployment as a recorded
     decision. Note it in ADR 0006 ("Redis not deployed: cache degrades
     gracefully, ~$12+/month for ElastiCache"). This is the cheapest choice.
  2. Add a Redis container as an ECS service, running redis:7 with service
     discovery, and set SPRING_DATA_REDIS_HOST on order-service. This costs a
     few cents per hour and shows the cache working.
  3. Add ElastiCache. This is the "proper" approach, but it adds cost and about
     10 minutes of provisioning.
  4. Quiet the log noise. Set SPRING_DATA_REDIS_HOST to something that fails
     quickly, or lower the CacheConfig log level. That hides the symptom, but I
     don't recommend it.

  If you pick option 2, I'll add the task definition, service and env var to
  ecs_services.tf (it already has uncommitted changes, so I'd review those
  first).

  For your screenshots or demo, include the CloudWatch lines as a deliberate
  point if you go with option 1. Say that the stock cache degrades gracefully
  without Redis, and that orders aren't affected because they don't depend on
  it.

  Why only warnings appear

  - There is almost no INFO logging in order-service. The only log.info in

  - The Redis warnings come from every stock lookup. The UI calls

    earlier.
  - The Broken pipe warning is harmless. AsyncRequestNotUsableException ...
    Broken pipe means the browser closed the SSE stream (/orders event stream),
    for example on a tab close, refresh, or ALB idle timeout. The server then
    tried to write to a closed connection.
  - Each event appears twice in your paste. It's the same line in CloudWatch's
    raw form and its formatted form, not duplicate logging.

  How to get evidence that an order flowed through

  CloudWatch Logs Insights over the order-service and inventory-service log
  groups can filter by trace ID, because the [order-service,<traceId>,<spanId>]
  prefix is already there. Warnings still carry the trace ID.

  For a demo, though, you want positive log lines. I'd add three log.info
  statements in order-service and one or two in inventory-service:

  - order created (id, status PENDING)
  - outbox event published to Kafka
  - inventory result received and the order moved to CONFIRMED
  - (inventory-service) reservation made

  Then CloudWatch shows the full PENDING → CONFIRMED story across both services
  under one trace ID.

  Other places that already show proof, with no code change:

  Why I don't recommend
  LOGGING_LEVEL_COM_ORDERFLOW_ORDER_CONFIG_CACHECONFIG=ERROR

  It works, but it's a trade-off I'd avoid here:

  - It hides the only sign that the cache is down. The two WARN lines are how
    you'd notice Redis is missing. The service would look healthy while every
    stock read waits out the 500 ms Redis timeout and then falls back to
    inventory-service.
  - It doesn't fix anything. Each request still tries to reach Redis. Only the
    logging changes.
  - It's easy to forget. The override sits in the task definition. If you add
    Redis later and it fails, the failure stays silent.

  If the noise bothers you, deploy Redis or disable the cache for this
  deployment, and record the choice. Silencing the logger is acceptable for a
  short demo recording, as long as you know what you're hiding.
