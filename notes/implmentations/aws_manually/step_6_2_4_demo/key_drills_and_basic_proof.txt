     apply -var image_tag=<new tag>. Without it, CloudWatch shows only the Redis

  3. Keep the Chrome/Edge unsafely-treat-insecure-origin-as-secure flag set for

  Demo script, in order

  1. It's really on AWS.
  - Show the ALB URL in the address bar.
  - Show the ECS console with all services RUNNING.

  2. Authentication (Keycloak).
  - Open the app. It redirects to /realms/orderflow on the ALB.
  - Log in as alice / alice-dev-pw.
  - Say that the token is validated by both services.

  3. Core flow: async order saga.
  - Create an order with in-stock items, such as SKU-1.
  - The status shows PENDING, then CONFIRMED without a page reload. That is the
    live SSE update.
  - Say what happened in between: order-service writes the order and an outbox
    row, the outbox publisher sends it to Kafka, inventory-service reserves
    stock and publishes RESERVED, and order-service confirms the order.

  4. Prove it in the logs (the key evidence).
  - Run a Logs Insights query over both log groups: fields @timestamp, @message
    | filter @message like /<traceId>/ | sort @timestamp.
  - It should show these lines in sequence under one trace ID:
    a. order created
    b. outbox event published
    c. stock reserved
    d. result published
    e. inventory result applied, order CONFIRMED

  5. Business rejection path.
  - Order a quantity larger than the stock.
  - The order ends as REJECTED. The inventory log shows "Stock rejected (wanted
    X, available Y)".
  - Confirm the stock count didn't drop.

  6. Idempotency (optional).
  - Send POST /api/orders twice with the same Idempotency-Key header, using curl
    or Swagger with alice's token.
  - You should get the same order back and no duplicate. I haven't checked the

  7. Graceful degradation (this is deliberate).
  - Show the Redis WARN lines from CacheConfig.
  - Say that the stock cache is optional, so the stock lookup falls back to

  - This is your ADR 0006 point, and the warnings are intentionally left

  8. Database proof (optional).

  Your repo doesn't support "50,000 orders and 6 forced outages" as written.

  - resilience.md (phase2/docs/resilience.md) records drills of 3,600 orders
    each. There are 3 drills run locally, 3 repeated as containers, and one

    them ran on AWS.
  - Your own errors-by-resume-bullet.md
    (notes/implmentations/errors-by-resume-bullet.md) deliberately leaves the
    bullet without numbers until you re-run.

  You have two options:
  - Run the drills on AWS (below) and quote whatever those runs show.
  - Reword the bullet to match what's recorded, such as "3,600-order drills, 0

  What AWS changes

  1. Kafka has no volume. ADR 0006 (phase2/docs/adr/0006-aws-choices.md) says
     topics vanish when the task restarts. Stopping or scaling the Kafka task
     loses events that were already published but not yet consumed. Those orders
     would stay PENDING forever, so it would look like a failure of your design
     when it is really a limit of the demo setup.
     - Simulate the Kafka outage as a network cut instead. Revoke the ingress
       rule on port 9092 in the Kafka security group (network.tf:139-147
       (phase2/infra/terraform/network.tf#L139-L147)). The broker keeps its
       data, and the services just can't reach it. Re-add the rule to end the
       outage.
     - The Kafka drill therefore tests the outbox, which is what it should test.
  2. RDS is private. drill-check.sql (scripts/drill-check.sql) needs a one-off
     ECS psql task, like db-init. drill_check.py (scripts/drill_check.py) and
     drill.sh (scripts/drill.sh) only work against local compose or Maven, so
     they need rewriting for AWS.
  3. No Prometheus or Grafana on AWS. Your evidence is the SQL checks and the
     CloudWatch INFO lines. You won't have the lag graph or the alert.
  4. Load needs a token. load_orders.py (scripts/load_orders.py) and the k6
     script need a Keycloak token against the ALB. I haven't checked how they
     get one, and the dev tokens are short-lived.

  The demo, step by step

  Setup
  1. Deploy the image with the INFO logs. Check that all services are at 1/1.
  2. Run the baseline check first. Run the SQL in drill-check.sql through the
     psql task, or note the current order count to use as a --baseline. It must
     pass on a clean system.
  3. Start the load against the ALB URL, for example 20 orders/s for 180 s.
     Record how many requests got a 201.

  Disruptions (start each 30 s into the load and let the system drain between
  runs)

  Drill: Kafka outage
  How to do it on AWS: Revoke the SG ingress on 9092 for 60 s, then re-add it
  What you should see: The API keeps returning 201. Orders stay PENDING, and the

  outbox rows stay unpublished. After the rule is back, they drain.
  ────────────────────────────────────────
  Drill: Longer Kafka outage
  How to do it on AWS: Same, for about 4 minutes
  What you should see: The same, with a larger backlog.
  ────────────────────────────────────────
  Drill: inventory-service down
  How to do it on AWS: aws ecs update-service --desired-count 0, wait 60 s, then

  set it back to 1
  What you should see: Orders stay PENDING, and then every order reaches
  CONFIRMED.
  ────────────────────────────────────────
  Drill: order-service killed
  How to do it on AWS: aws ecs stop-task on the one task
  What you should see: The ALB returns 5xx while the task restarts. Those
  requests never got a 201, so they aren't counted as lost.
  ────────────────────────────────────────
  Drill: Redelivery (the idempotent-consumer proof)
  How to do it on AWS: Kill inventory-service mid-load (stop-task), so Kafka
  redelivers unacknowledged messages when it restarts
  What you should see: The logs show the Message … already processed; duplicate
  ignored INFO line.

  Proof after each drill
  - The SQL checks pass:
    - orders with a 201 equal rows in orders
    - 0 orders still PENDING
    - 0 unpublished outbox rows in either service
    - reserved quantity per SKU equals the CONFIRMED quantity
    - no order has more than one OrderCreated row
  - Show the CloudWatch Logs Insights query for the duplicate-ignored lines.
    This is the visible evidence of at-least-once redelivery being absorbed.
  - Add a final check on the processed_messages count against the order count,
    as in your local runs.

  - "0 lost" covers orders that got a 201. The order-service drill produces
    errors for requests that were never acknowledged. Your resilience.md already

  - Kafka's lack of a volume is a demo limit. A real deployment needs a durable
    Kafka, such as MSK.

  What I wrote
  - Disruption script: aws_drill.sh (scripts/aws_drill.sh) takes kafka,

> What is a drained system?
  How do we use CloudShell?

● A drained system is one where no work is still moving through the order
  pipeline. The term comes from your own drill notes. Before you stop Kafka,
  nothing may be in flight. That means:

     /orderflow/order-service and /orderflow/inventory-service. Type orderflow
     to filter the list.
  4. Set the time range. Use the picker at the top right and choose Absolute.
     Start a few minutes before you began the drill and end after the last order
     reached CONFIRMED. The default is the last hour, which is fine if the
     drill was recent.
  5. Paste the query and run it. Click Run query. The query to paste is below.

  Main query (order-service's view):
  filter @message like /created for customer|is now CONFIRMED|is now REJECTED/
  | parse @message /(?<kind>created for customer|is now CONFIRMED|is now
  REJECTED)/
  | stats count(*) by kind

  Optional second query (inventory-service's view, including duplicates):
  filter @message like /created for customer|Stock reserved for order|Stock
  rejected for order|duplicate ignored/
  | parse @message /(?<kind>created for customer|Stock reserved for order|Stock
  rejected for order|duplicate ignored)/
  | stats count(*) by kind

  Reading the result

  The result is a small table with one row per kind and its count.

  - Main query: created for customer should equal is now CONFIRMED plus is now
    REJECTED.
  - Second query: created for customer should equal Stock reserved plus Stock
    rejected. duplicate ignored is shown separately and should not be added to
    either side. It can legitimately be 0.
  - Expected REJECTED count: 0, because stock was plentiful.
  - If created is higher: some orders haven't finished, or something was lost.
    Wait a minute and run it again.
  - If a row is missing: there were no such lines in that time range, or the
    image without the INFO lines is still deployed.

  Common problems

  - No results at all: widen the time range first. Then check that you selected
    both log groups and the right region.
  - Counts look too high or low: the time range includes earlier orders, such as
    your smoke-test orders. Narrow it to the drill, or subtract the baseline
    you noted.
  - Logs lag: lines can take up to about a minute to appear, so re-run if the
    counts are still moving.
  - Unverified query: I haven't run these queries. If the parse line errors,
    send me the error.

> What are the steps to implement this drill: order-service killed

● Like the inventory drill, this needs no Terraform changes. Console steps
  first, then the load version and the CLI equivalent.

  Before you start

  1. Check the stack. In ECS → cluster orderflow, kafka, inventory-service and
     order-service should each show 1/1 running.
  2. Check it's drained. Create one order in the UI and wait for CONFIRMED.
     Nothing should show PENDING.
  3. Note the starting point. Run the Logs Insights count query and write down
     the created for customer count, or subtract it later.
  4. Have the INFO log lines deployed. The log evidence depends on them.

  The drill (console)

  1. Create orders just before the stop
  - Create about 5 orders in the UI right before you stop the task. Some of them
    will still be in flight when the task stops. Those are the ones that show
    the outbox survives the stop.

  2. Stop the order-service task
  - Go to ECS → Clusters → orderflow → Services → order-service → Tasks tab.
  - Select the running task and click Stop. Write down the time.
  - The service notices 0 running against a desired count of 1 and starts a
    replacement on its own.

  3. Observe the outage
  - The UI and API return errors, usually 503, because the ALB has no healthy
    target.
  - Any request that fails never got a 201, so that order isn't acknowledged and
    doesn't count as lost.
  - The live status stream in the UI drops.
  - The replacement needs about 1–3 minutes: Spring Boot start, Flyway, and the
    ALB health check (the service has a 120 s grace period).

  4. Watch recovery
  - Watch the service's Events tab for the new task starting and then
    registering with the target group.
  - Check EC2 → Target Groups for the order-service target going healthy.
  - Wait until the service shows 1/1 running.

  5. Verify
  - The orders you created before the stop should end up CONFIRMED. Refresh the
    UI.
  - Run the Logs Insights count query over both log groups. created for customer
    should equal CONFIRMED plus REJECTED.
  - Expected REJECTED count: 0.

  With a load (for numbers)

  1. From your machine, run:
  python scripts/load_orders.py --rate 20 --duration 300 --base-url <ALB_URL>
  --keycloak-url <ALB_URL>
  2. Stop the order-service task at about 30 seconds.
  3. Keep the script's created_201 count and its failure count. The failures are
     expected: roughly the downtime in seconds times 20.
  4. After the drain, compare the created for customer log count with
     created_201.
  5. The log count should be equal to or slightly higher than created_201. The
     difference is orders that were saved but whose 201 never reached the
     client. resilience.md (phase2/docs/resilience.md) names this gap, and the
     local runs saw none.
  6. A hard kill can lose the last buffered log lines, so a small gap in the
     other direction is possible too. Don't claim an exact match.

  CLI equivalent

  aws ecs list-tasks --cluster orderflow --service-name order-service --query
  'taskArns[0]' --output text
  aws ecs stop-task --cluster orderflow --task <TASK_ID> --reason drill
  aws ecs wait services-stable --cluster orderflow --services order-service

  What this shows, and its limits

  - It shows: an order-service outage doesn't lose any order that got a 201.
    Rows committed before the stop get published after the restart, and results
    that inventory-service produced meanwhile wait in Kafka.
  - A stop isn't a crash. ECS sends SIGTERM and only force-kills after 30
    seconds. The local drill used taskkill /F, which is harsher. There is no
    clean console way to hard-kill a Fargate task.
  - What to claim: say "stopped", not "crashed". The outage is also longer than
    the local 26 seconds, because of Fargate startup.
  - Screenshots:
    - the ECS service at 0/1 and then 1/1
    - the browser error during the outage
    - the orders CONFIRMED afterwards
    - the Logs Insights counts
  - Restore: nothing to do, because the service replaces the task itself. If it
    doesn't come back, check the Events tab first. The deployment circuit
    breaker or a failing health check is the likely cause.

  Why the drill uses a load at all
  - To make the claim "N orders, 0 lost" you need a count of acknowledged orders
    to compare against. created_201 from the load script gives you that.
  - The load also guarantees orders are in flight when the task stops. With 5
    manual orders you might get none in flight.
  - It keeps the AWS result comparable with your local drills, which used the
    same script at the same rate.

  When to skip it
  - If you only want to demonstrate the behaviour, create about 10 orders by
    hand and stop the task. That is enough for a demo, but it supports no
    numbers in the bullet.
  - If you use the load, keep the 20 orders/s rate so it matches the local runs.

  - A rolling deploy briefly runs two order-service tasks that publish the same

    is above 0, that run also gives you redelivery evidence at no extra cost.

    system, so the two runs don't mix in the logs.

  load leaves lots of orders and logs behind. If you want the kill drill's
  counts to be easy to read, run it first, note the baseline, and then run 24c.

> What are the steps to implement this test: Redelivery (the
  idempotent-consumer proof)

● This test replays the orders.events topic to inventory-service, so every event
  it already processed arrives a second time. If the consumer is idempotent,
  each one is ignored and nothing changes. It is a deliberate replay, not a
  natural outage, so describe it that way.

  Prerequisites

  - ECS Exec must be on for the Kafka task, because the rewind command runs
    inside the Kafka container. Do the IAM policy and ECS Exec update from the
    earlier Option A answer. You don't need the init-process change here, since
    only kill -STOP has the PID 1 problem.
  - Enabling ECS Exec replaces the Kafka task and empties the topics. Do it
    first, before creating the orders you want to replay.
  - The INFO log lines must be deployed.

  Steps

  1. Create the data to replay
  - After the new Kafka task is running, create about 20 orders (by hand, or
    load_orders.py --rate 20 --duration 30).
  - Wait until all are CONFIRMED and none are PENDING.

  2. Record the baseline
  - Note the time.
  - Run the Logs Insights count query and write down Stock reserved and Stock
    rejected.
  - If you have the SQL check task, also record the processed_messages count and
    the reserved stock per SKU.

  3. Stop the consumer
  - ECS → inventory-service → Update → Desired tasks 0.
  - Wait for 0 running. The consumer group must be empty, or Kafka refuses the
    reset.

  4. Rewind the consumer group (CloudShell)
  - Get the task ID and open a shell as in the earlier answer:
  aws ecs list-tasks --cluster orderflow --service-name kafka --query
  'taskArns[0]' --output text
  aws ecs execute-command --cluster orderflow --task <TASK_ID> --container kafka
  --interactive --command "/bin/sh"
  - Inside the shell, the script path is my assumption for this image:
  /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092
  --group inventory-service --describe
    Note LOG-END-OFFSET for orders.events. That is the number of records that
    will be replayed.
  - Preview the reset:
  /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092
  --group inventory-service --topic orders.events --reset-offsets --to-earliest
  --dry-run
  - Apply it by repeating the command with --execute instead of --dry-run.
  - Run --describe again. The lag should now equal the log-end offset.
  - The group id inventory-service is confirmed in the code.

  5. Restart the consumer
  - Set inventory-service Desired tasks back to 1 and wait for RUNNING.
  - It reads the whole topic again.

  6. Verify
  - In Logs Insights, set the time range to start when you restarted
    inventory-service, then run:
  filter @message like /duplicate ignored|Stock reserved for order|Stock
  rejected for order/
  | parse @message /(?<kind>duplicate ignored|Stock reserved for order|Stock
  rejected for order)/
  | stats count(*) by kind
  - Expected result:
    - duplicate ignored equals the log-end offset from step 4
    - Stock reserved and Stock rejected are 0 in this window
  - The UI should still show the same CONFIRMED orders.
  - If you have the SQL check, processed_messages and the reserved stock should
    be unchanged.

  What this proves

  - The consumer absorbed a full redelivery with no new reservations and no new
    result events. That is the "idempotent consumers absorbing at-least-once
    redelivery" part of the bullet.
  - It shows the consumer side only. It doesn't show the producer creating
    duplicates on its own.
  - The count of duplicate ignored lines is the evidence.
  - A replay of 20 orders is a demo. It doesn't support the 50,000-order figure.

  An alternative without touching the Kafka task

  You can run the same kafka-consumer-groups.sh command from a one-off ECS task
  using the apache/kafka image. It would need the inventory-service security
  group to reach port 9092. That is more console clicking and I haven't verified
  it, so ECS Exec is the simpler route if you're already enabling it.
