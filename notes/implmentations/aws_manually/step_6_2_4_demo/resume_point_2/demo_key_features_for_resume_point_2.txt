## What AWS changes

1. **Kafka has no volume.** [ADR 0006](phase2/docs/adr/0006-aws-choices.md) says topics vanish when the task restarts. Stopping or scaling the Kafka task loses events that were already published but not yet consumed. Those orders would stay PENDING forever, so it would look like a failure of your design when it is really a limit of the demo setup.
   - Simulate the Kafka outage as a **network cut** instead. Revoke the ingress rule on port 9092 in the Kafka security group ([network.tf:139-147](phase2/infra/terraform/network.tf#L139-L147)). The broker keeps its data, and the services just can't reach it. Re-add the rule to end the outage.
   - The Kafka drill therefore tests the outbox, which is what it should test.
2. **RDS is private.** [drill-check.sql](scripts/drill-check.sql) needs a one-off ECS psql task, like `db-init`. [drill_check.py](scripts/drill_check.py) and [drill.sh](scripts/drill.sh) only work against local compose or Maven, so they need rewriting for AWS.
3. **No Prometheus or Grafana on AWS.** Your evidence is the SQL checks and the CloudWatch INFO lines. You won't have the lag graph or the alert.
4. **Load needs a token.** [load_orders.py](scripts/load_orders.py) and the k6 script need a Keycloak token against the ALB. I haven't checked how they get one, and the dev tokens are short-lived.

## The demo, step by step

**Setup**
1. Deploy the image with the INFO logs. Check that all services are at 1/1.
2. Run the baseline check first. Run the SQL in drill-check.sql through the psql task, or note the current order count to use as a `--baseline`. It must pass on a clean system.
3. Start the load against the ALB URL, for example 20 orders/s for 180 s. Record how many requests got a `201`.

**Disruptions** (start each 30 s into the load and let the system drain between runs)

| Drill | How to do it on AWS | What you should see |
|---|---|---|
| Kafka outage | Revoke the SG ingress on 9092 for 60 s, then re-add it | The API keeps returning 201. Orders stay PENDING, and the outbox rows stay unpublished. After the rule is back, they drain. |
| Longer Kafka outage | Same, for about 4 minutes | The same, with a larger backlog. |
| inventory-service down | `aws ecs update-service --desired-count 0`, wait 60 s, then set it back to 1 | Orders stay PENDING, and then every order reaches CONFIRMED. |
| order-service killed | `aws ecs stop-task` on the one task | The ALB returns 5xx while the task restarts. Those requests never got a 201, so they aren't counted as lost. |
| Redelivery (the idempotent-consumer proof) | Kill inventory-service mid-load (`stop-task`), so Kafka redelivers unacknowledged messages when it restarts | The logs show the `Message … already processed; duplicate ignored` INFO line. |

**Proof after each drill**
- The SQL checks pass:
  - orders with a 201 equal rows in `orders`
  - 0 orders still PENDING
  - 0 unpublished outbox rows in either service
  - reserved quantity per SKU equals the CONFIRMED quantity
  - no order has more than one `OrderCreated` row
- Show the CloudWatch Logs Insights query for the duplicate-ignored lines. This is the visible evidence of at-least-once redelivery being absorbed.
- Add a final check on the `processed_messages` count against the order count, as in your local runs.
