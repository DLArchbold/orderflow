  2. Duplicate-ignored query

  The log line is Message {} already processed; duplicate ignored
  (InventoryService.java:57 (services/inventory-service/src/main/java/com/orderf
  low/inventory/service/InventoryService.java#L57)). It comes only from
  inventory-service. In CloudWatch → Logs Insights, select
  /orderflow/inventory-service, set the time range to cover the drill, and run:

  filter @message like /already processed; duplicate ignored/
  | stats count(*) as duplicates_ignored

  For the visible evidence, list the lines instead:
  fields @timestamp, @message
  | filter @message like /already processed; duplicate ignored/
  | sort @timestamp asc
  | limit 50

  If the count is 0, no redelivery happened, so don't claim it. Stopping
  inventory-service gracefully won't produce duplicates (see the earlier answer
  on this). Use the offset-replay method from your notes.

  Load

  Run scripts/load_orders.py from your laptop, pointed at the ALB:

  python scripts/load_orders.py --rate 20 --duration 180 --base-url http://<ALB>
  --keycloak-url http://<ALB>

  It prints a JSON summary at the end with created_201. That is the number you
  add to the baseline in the first SQL check.

  Disruption

  These are manual commands, started about 30 seconds into the load. You can
  type each into a second terminal or CloudShell.

  ┌────────────────┬────────────────────────────────────────────────────────┐
  │     Drill      │                        Command                         │
  ├────────────────┼────────────────────────────────────────────────────────┤
  │                │ aws ecs update-service --cluster orderflow --service   │
  │ inventory down │ inventory-service --desired-count 0, wait about 60 s,  │
  │                │ then set --desired-count 1                             │
  ├────────────────┼────────────────────────────────────────────────────────┤
  │ order-service  │ aws ecs stop-task --cluster orderflow --task           │
  │ killed         │ <task-arn>                                             │
  ├────────────────┼────────────────────────────────────────────────────────┤
  │                │ Console route: stop or freeze Kafka as in your         │
  │ Kafka outage   │ option_a_substeps.txt notes. Stopping the task loses   │
  │                │ the topics, so use the freeze (Option A).              │
  ├────────────────┼────────────────────────────────────────────────────────┤
  │ Redelivery     │ Scale inventory-service to 0, rewind the consumer      │
  │                │ group (needs ECS Exec on Kafka), then scale back to 1. │
  └────────────────┴────────────────────────────────────────────────────────┘

  Sequence

  1. Run the wrapper for a baseline. It must pass on the clean system.
  2. Start the load in terminal 1.
  3. Apply the disruption in terminal 2, 30 s in. Restore the service
     afterwards.
  4. When the load finishes, wait for the drain (the wrapper can poll until
     still_pending is 0).
  5. Run the wrapper again with --created <created_201> --baseline <n>. It
     prints PASS/FAIL.
  6. Run the Logs Insights duplicate query.
