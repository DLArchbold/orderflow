● terraform destroy deletes everything Terraform manages. Nothing is kept: your
  config is built to be torn down, and you can rebuild it with the same steps
  you've just followed.

  What gets deleted

  Resource: ECS cluster, 5 services, task definitions
  Effect: Gone. Running tasks are stopped.
  ────────────────────────────────────────
  Resource: ALB, target groups, listener rules
  Effect: Gone. The app_url address is dead and will be different next time.
  ────────────────────────────────────────
  Resource: RDS instance
  Effect: Deleted with all data. skip_final_snapshot = true and
  backup_retention_period = 0 mean there is no snapshot and no backup
  (data.tf:67-69 (phase2/infra/terraform/data.tf#L67-L69)). Orders and
  inventory rows are lost.
  ────────────────────────────────────────
  Resource: Secrets Manager secrets (DB, Keycloak)
  Effect: Deleted immediately, with no recovery window (data.tf:41
  (phase2/infra/terraform/data.tf#L41)). Passwords are regenerated next time.
  ────────────────────────────────────────
  Resource: ECR repositories and your pushed images
  Effect: Deleted. force_delete = true removes them even though they contain
  images (data.tf:29 (phase2/infra/terraform/data.tf#L29)).
  ────────────────────────────────────────
  Resource: VPC, subnets, security groups, IAM roles, log groups, Cloud Map
  Effect: Gone.
  ────────────────────────────────────────
  Resource: Keycloak users and realm state
  Effect: Gone. It runs in dev mode with no persistent storage.

  Not affected: your AWS account, the budget alert (if it was created outside
  Terraform; check, since budget_email is a Terraform variable, so the budget is
  probably destroyed too), and your code and notes. The local terraform.tfstate
  stays and then holds an empty state.

  If the budget alert is managed by this config, you'd lose your cost alarm
  until the next apply. To keep it, remove it with terraform destroy -target=...
  instead, or accept that and re-create it on the next apply. Run terraform
  state list | Select-String budget to see.

  You rebuild rather than reverse, and these are the same steps as before:

  1. Create everything: terraform apply -var "image_tag=$tag" would fail on
     image pulls, since ECR is empty. So create ECR first:

     This is the one deliberate use of -target. Then follow with the full apply
     at step 4.
  2. Push images (step 3): ECR login with the throwaway DOCKER_CONFIG, then

  3. Create the databases: the databases are new, so the db-init task has to run

     crash-loop until this has run, then recover on their own, or force it with
     aws ecs update-service --cluster orderflow --service order-service
     --force-new-deployment.

     config injects it into Keycloak and the frontend automatically.

  Order is the catch: a full apply before step 3's push means the app services
  fail to pull images until you push. They keep retrying, so pushing afterwards
  works, but you'll see errors in between.

  Cheaper alternative to a full destroy

  If you only want to stop the hourly cost but keep RDS data and ECR images for
  a short break, scale the services to zero:

  foreach ($s in
  "kafka","keycloak","inventory-service","order-service","frontend") {
    aws ecs update-service --cluster orderflow --service $s --desired-count 0
  --region us-east-1
  }

  That stops the Fargate cost. But the ALB (~$0.02/hr) and RDS keep billing, so
  it only suits a break of hours, not days. Also, Terraform will want to set
  desired_count back to 1 on the next apply, which is fine. For anything longer
  than a day, destroy.

  Before destroying, if you want to keep anything, such as a record of a working
  deploy, save it first: terraform output > outputs.txt, and screenshot or copy
  the app. The state file holds the generated passwords, so don't commit it.

  2. Push images

  2a. Start in the repo root and set variables
  cd "C:\Users\WJ\Desktop\Work 2023-05-12\Project\orderflow"
  $tf  = ".\phase2\infra\terraform\"
  $tag = git rev-parse --short HEAD
  $reg = (terraform "-chdir=$tf" output -json ecr_repositories |

  $tag
  $reg
  - $tag should print a short SHA, and $reg should list three repo URLs. If
    either is empty, the ECR apply didn't finish.
  - Re-using the same tag only works if HEAD hasn't moved. If you've made
    commits since, $tag is different, so pass that new value as image_tag in the
    full apply. The image content must match the commit you tag it with, so
    commit or stash changes before building.

  2b. Confirm AWS credentials
  aws sts get-caller-identity
  If this fails, run aws sso login and retry.

  2c. Create the throwaway Docker config (once per window)
  $env:DOCKER_CONFIG = Join-Path $env:TEMP "docker-ecr"
  New-Item -ItemType Directory -Force $env:DOCKER_CONFIG | Out-Null
  Set-Content (Join-Path $env:DOCKER_CONFIG "config.json")
  '{"auths":{"example.invalid":{}}}' -Encoding ascii
  This avoids the Windows Credential Manager "stub received bad data" error. The
  folder survives a destroy, so on a re-run you only need to repeat the
  $env:DOCKER_CONFIG line if you opened a new window.

  2d. Log in to ECR
  $pw = aws ecr get-login-password --region us-east-1
  docker login --username AWS --password $pw
  702623019395.dkr.ecr.us-east-1.amazonaws.com
  Expect Login Succeeded. The token lasts 12 hours. The registry host is your
  account ID, which doesn't change between destroys.

  2e. Build the three images
  docker build --platform linux/amd64 -t "$($reg.'order-service'):$tag"
  services/order-service
  docker build --platform linux/amd64 -t "$($reg.'inventory-service'):$tag"
  services/inventory-service
  docker build --platform linux/amd64 -t "$($reg.'frontend'):$tag" frontend
  Each command must be on one line, with the build path last. Docker's local
  cache holds the layers from your earlier builds, so these should finish in
  seconds to a couple of minutes, unless you changed dependencies or code. The
  repo URLs are the same after a destroy, so the cached images are tagged
  correctly.

  2f. Push them
  docker push "$($reg.'order-service'):$tag"
  docker push "$($reg.'inventory-service'):$tag"
  docker push "$($reg.'frontend'):$tag"
  The ECR repos are empty after a destroy, so every layer uploads again. That is
  the slowest part.

  2g. Verify
  aws ecr describe-images --repository-name orderflow-order-service --region
  us-east-1 --query "imageDetails[].imageTags"
  aws ecr describe-images --repository-name orderflow-inventory-service --region
  us-east-1 --query "imageDetails[].imageTags"
  aws ecr describe-images --repository-name orderflow-frontend --region
  us-east-1 --query "imageDetails[].imageTags"
  Each should list $tag.

  2h. Clean up when you're done for the session
  Remove-Item Env:DOCKER_CONFIG
  Remove-Item -Recurse -Force (Join-Path $env:TEMP "docker-ecr")
  The folder holds the ECR token in plain text. Don't clean up before step 3's
  full apply if you still need to push again.
