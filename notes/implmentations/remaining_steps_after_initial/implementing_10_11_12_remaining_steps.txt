● Those are fair questions. One of my sentences was wrong, which I explain under
  your last question.

  What "free virtual users" means
  - A virtual user (VU) in k6 is a worker that runs the script's default
    function one pass at a time. Here one pass is one POST /api/orders request
    and its response check. That pass is called an iteration.
  - A VU can only work on one iteration at a time. While it waits for a
    response, it's busy.
  - This test uses the constant-arrival-rate executor, which means "start 600
    iterations every second, whether or not earlier ones have finished." To
    start one, k6 needs a free VU. The script allows 100 pre-allocated VUs and
    up to 300 in total (preAllocatedVUs: 100, maxVUs: 300).
  - Busy VUs ≈ rate × response time. At 600/s with 5 ms responses, about 3 VUs
    are busy. If responses take 2 s, about 1,200 would be needed, but only 300
    exist. Once all 300 are waiting on slow responses, there is no free VU left.

  Whether "dropped iterations" means requests that didn't return 201
  - No, it's different. A dropped iteration is one k6 scheduled but never
    started because no VU was free. No request was sent, so it can't be a
    non-201 and it doesn't count in http_req_failed (which stayed at 0%).
  - It means the load generator couldn't deliver the load you asked for. In run
    2, 5,954 of the 18,000 scheduled orders were never sent, so the server saw
    397 requests/s, not 600.
  - A failed request is one that was sent and got an error or timeout. That's
    what happened in the host runs, with the hung and reset requests.

  Why 500 ms matters, and a correction
  - 500 ms is the pass line in the k6 script, http_req_duration: ['p(95)<500'],
    with http_req_failed < 1% alongside it. I used it as the cut for "bad" runs.
  - I wrote that it's "a stricter cut than the table shows". That was wrong. The
    table has no pass/fail column, and 500 ms is the project's own threshold,
    not a stricter one. Runs 2, 5 and 7 are the ones that would fail it.
  - p95 is the time that 95% of requests came in under. Run 1 and run 8 had a
    p95 of 12 and 17 ms, so they pass. Yet they still had pressure: 127 requests
    waiting in run 1, and 53 and 232 dropped iterations.

  A gap this shows
  - The script has no threshold on dropped iterations. A run that fails to
    deliver the requested rate can still pass.
  - Run 8 passed at 583 achieved against 600, and run 1 passed with 293
    against 300.
  - A threshold like dropped_iterations: ['count<1'], or a check that the
    achieved rate is at least 95% of the target, would make k6 flag those runs.
    Do you want me to add it to create-orders.js?
