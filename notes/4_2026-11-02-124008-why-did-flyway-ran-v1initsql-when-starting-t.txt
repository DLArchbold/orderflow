> Why did Flyway ran V1__init.sql when starting the spring boot project in
  services/order-service with mvn spring-boot:run?

● Flyway ran V1__init.sql because of Spring Boot auto-configuration. You didn't
  have to configure anything.

  1. Flyway is on the classpath. pom.xml:22-23
     (services/order-service/pom.xml#L22-L23) declares flyway-core and
     flyway-database-postgresql.
  2. Spring Boot's FlywayAutoConfiguration switches on by default. It activates
     when Flyway is on the classpath and a DataSource exists.
     spring.flyway.enabled defaults to true, and application.yml
     (services/order-service/src/main/resources/application.yml) never sets it
     to false.
  3. It uses your datasource. The settings in spring.datasource
     (jdbc:postgresql://localhost:5432/orders) tell Flyway which database to
     connect to.
  4. It scans the default migration location. That location is
     classpath:db/migration, and V1__init.sql
     (services/order-service/src/main/resources/db/migration/V1__init.sql) sits
     there. The V<version>__<description>.sql filename is what Flyway looks for.
  5. The migration runs before JPA starts. Spring Boot makes the
     EntityManagerFactory depend on Flyway. On startup Flyway checks its
     flyway_schema_history table. If it doesn't exist or V1 isn't recorded,
     Flyway runs V1__init.sql and records it.

  The ordering matters because of ddl-auto: validate (application.yml:12
  (services/order-service/src/main/resources/application.yml#L12)). Hibernate
  only checks that the tables match your entities. Flyway has to create them
  first.

  You'll see it run on the first start against a fresh orders database. Later
  starts skip V1, because Flyway sees it's already applied and only checks its
  checksum. If you edit V1 after it has run, startup fails with a checksum
  mismatch.

  To turn this off, set spring.flyway.enabled: false. To change the scripts'
  location, set spring.flyway.locations.

> How do enums work in Java and how does the allowedNext() method function?

  Read 1 file (ctrl+o to expand)

● How Java enums work

  An enum is a special class with a fixed set of instances. PENDING, CONFIRMED,
  REJECTED, CANCELLED are the only four OrderStatus objects that will ever
  exist.

  - Each constant is a public static final instance of the enum, created once
    when the class loads.
  - You can't call new OrderStatus(). The constructor is implicitly private.
  - Because there is exactly one instance of each constant, you can compare them
    with ==.
  - An enum is a full class. It can have fields, constructors and methods, and
    it can implement interfaces. allowedNext() is one of those methods.
  - The compiler gives you values(), valueOf(String), name() and ordinal().
    Order uses this when it prints status in its error message.
  - The semicolon on line 6 is required because members follow the constants.

  How allowedNext() works

  OrderStatus.java:8-14 (services/order-service/src/main/java/com/orderflow/orde
  r/domain/OrderStatus.java#L8-L14) is a state machine written as a switch
  expression on this. this is whichever constant the method was called on.

  ┌─────────────────────┬────────────────────────────────┐
  │   Current status    │          Allowed next          │
  ├─────────────────────┼────────────────────────────────┤
  │ PENDING             │ CONFIRMED, REJECTED, CANCELLED │
  ├─────────────────────┼────────────────────────────────┤
  │ CONFIRMED           │ CANCELLED                      │
  ├─────────────────────┼────────────────────────────────┤
  │ REJECTED, CANCELLED │ none (Set.of())                │
  └─────────────────────┴────────────────────────────────┘

  - -> arms don't fall through, so no break is needed.
  - return switch: the switch is an expression that produces a value.
  - No default is needed, because the compiler knows every enum constant is
    covered. If you add a new constant like SHIPPED and forget to handle it
    here, this stops compiling. That's the main advantage over a default branch.
  - Set.of(...) returns an immutable set, so callers can't change the rules.
    Set.of() is an empty set, which marks REJECTED and CANCELLED as terminal
    states.

  How Order uses it

  Order.transitionTo() (Order.java:33-38 (services/order-service/src/main/java/c
  om/orderflow/order/domain/Order.java#L33-L38)) calls
  status.allowedNext().contains(next). If the target isn't allowed, it throws
  IllegalStateException. So reject() on a CONFIRMED order fails, and nothing can
  leave a terminal state.

> Is this the way to represent one-to-many relationships between tables in
  JPA/Hibernate?
  @ElementCollection
      @CollectionTable(name = "order_lines", joinColumns = @JoinColumn(name =
  "order_id"))
      @OrderColumn(name = "line_no")
      private List<OrderLineEmbeddable> lines = new ArrayList<>();

● It's one way, and it fits this case. The usual way is @OneToMany with a
  separate @Entity.

  Two ways to map one-to-many

  @OneToMany / @ManyToOne is the standard way. The child is a full entity with
  its own @Id, and the two sides are linked as entities:

  @OneToMany(mappedBy = "order", cascade = ALL, orphanRemoval = true)
  private List<OrderLineEntity> lines;      // child has @ManyToOne OrderEntity
  order

  Use it when the child has its own identity or lifecycle. Examples are querying
  children directly, referencing them from other tables, or giving them their
  own relationships.

  @ElementCollection is what you pasted. The child is a value type
  (@Embeddable), not an entity. It has no id and no repository, and it exists
  only as part of its parent. Hibernate always loads, saves and deletes the
  children through the parent.

  Why @ElementCollection suits order_lines

  - The table's primary key is (order_id, line_no), so a line has no identity
    apart from its order and position.
  - A line is just sku and quantity. Nothing else points at it.
  - You never need to fetch or save a line on its own.
  - It needs fewer classes and no two-way order / lines bookkeeping.

  Trade-off

  Hibernate handles changes to an element collection coarsely. Changing a list
  that has no @OrderColumn makes Hibernate delete all the child rows and
  re-insert them. With @OrderColumn it can do smaller updates, but inserting or
  removing in the middle still shifts indexes. That doesn't matter here, because
  order lines are written once and rarely edited.

  If lines later get their own id, status or relationships (for example a
  per-line shipment), switch to @OneToMany with an OrderLineEntity. Your schema
  would need a surrogate key for that.

> What are the needed changes if I want OrderLine to be an Entity as well?

● Three things change: the schema, the new child entity, and the parent's
  mapping.

  1. Schema: add V2__order_lines_id.sql

  An entity needs its own @Id, and order_lines currently has only the composite
  key (order_id, line_no). The simplest fix is a surrogate key. Don't edit
  V1__init.sql. Flyway has already applied it, so changing it causes a checksum
  mismatch. Add a new migration instead:

  ALTER TABLE order_lines DROP CONSTRAINT order_lines_pkey;
  ALTER TABLE order_lines ADD COLUMN id BIGINT GENERATED ALWAYS AS IDENTITY
  PRIMARY KEY;
  ALTER TABLE order_lines ADD CONSTRAINT uq_order_lines_order_line UNIQUE
  (order_id, line_no);

  Existing rows get ids automatically, and the unique constraint keeps one
  line_no per order.

  This new file takes version 2, so that one has to be renamed to V3__... when
  you get there.

  2. New OrderLineEntity, replacing the @Embeddable

  @Table(name = "order_lines")

      private Long id;

      @Column(name = "line_no", nullable = false) private int lineNo;
      @Column(nullable = false) private String sku;
      @Column(nullable = false) private int quantity;

      protected OrderLineEntity() {}
      OrderLineEntity(OrderEntity order, int lineNo, String sku, int quantity) {
  ... }
      // getters
  }

  GenerationType.IDENTITY matches the GENERATED ALWAYS AS IDENTITY column.
  Delete OrderLineEmbeddable.

  3. OrderEntity: swap the mapping

  Replace @ElementCollection, @CollectionTable and @OrderColumn with:

  @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval =
  true)
  @OrderBy("lineNo ASC")
  private List<OrderLineEntity> lines = new ArrayList<>();

  public void addLine(String sku, int quantity) {
      lines.add(new OrderLineEntity(this, lines.size(), sku, quantity));
  }

  - mappedBy = "order": the child owns the foreign key through its @ManyToOne,
    so the parent doesn't write the join column.
  - cascade = ALL: saving the order saves its lines, and deleting the order
    deletes them.
  - orphanRemoval = true: a line removed from the list is deleted from the
    table.
  - @OrderBy("lineNo ASC"): replaces @OrderColumn. lineNo is now an ordinary
    field you set yourself. @OrderColumn would also work with mappedBy, but it
    is easy to get wrong. Setting lineNo in addLine is more explicit.
  - Both sides are set: the helper makes sure the child's order reference is
    filled. If it is null, the insert fails on order_id NOT NULL.

  Things to watch

  - Repository: you still only need JpaRepository<OrderEntity, UUID>. Add an
    OrderLineRepository only if you query lines on their own.
  - N+1 queries: listing orders and then reading lines runs one extra query per
    order. Use @EntityGraph(attributePaths = "lines") or a join fetch query on
    the list endpoint.
  - equals / hashCode: if you put lines in a Set or compare them, base equality
    on the id or a business key, not on the default object identity.
