    Why `acks: all` matters: `acks` sets when the broker tells the producer the write succeeded. `acks=0` never waits (messages can vanish unnoticed), `acks=1` waits only for the partition leader (if the leader dies before followers copy the record, it is lost although the producer was told it succeeded), and `acks=all` waits until all in-sync replicas have it, so the record survives losing the leader. Two reasons it is required here: the outbox publisher (step 13e) calls `markPublished()` only after the ack, so the ack must mean the message is durable, otherwise a row could be marked published, the event lost, and nothing would ever retry it (the order would stay PENDING forever); and Kafka refuses to enable `enable.idempotence` without `acks=all`. It costs a little latency and works together with the topic's `min.insync.replicas`, which rejects writes when too few replicas are available. With `replicas(1)` on the local topic, `acks=all` behaves like `acks=1`, but set it now so the config stays correct on a multi-broker cluster (for example on AWS).
