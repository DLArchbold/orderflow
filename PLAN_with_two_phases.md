    What idempotence means here: with `enable.idempotence: true` the broker gives the producer an ID and the producer numbers each record per partition, so if an ack is lost and the producer retries, the broker recognises the sequence number and drops the duplicate (it still acks). It requires `acks=all`, `retries` above 0 and at most 5 in-flight requests per connection (recent clients default to this since Kafka 3.0, but set it explicitly so the intent is visible). Its limits: it protects only one producer session, so after an app restart the producer gets a new ID and a re-send can still duplicate (the outbox publisher hits exactly this: send, crash before `markPublished()`, send again), and it covers only the producer-to-broker hop, not a consumer reprocessing a message. That is why step 14 still needs the idempotent consumer with `processed_messages`.
    What "failure before the offset commit" means: an offset is a consumer's bookmark in a partition, and the consumer group commits it to tell Kafka "I have processed everything up to here"; after a restart or rebalance the consumer resumes from the last committed offset. The usual order is poll message 42, process it (reserve stock in Postgres), then commit the offset. If the consumer crashes or loses its partition in a rebalance after processing but before the commit, the reservation is already saved while Kafka still has the old offset (41), so message 42 is delivered again. The producer sent it only once; the duplicate comes from the consumer side, which producer idempotence cannot prevent. Committing after processing gives at-least-once delivery (a crash can repeat a message but never lose one), whereas committing before processing would be at-most-once (a crash could lose it). Step 14 handles the repeat: the consumer inserts the message id into `processed_messages` in the same transaction as the stock reservation, so the second delivery hits the unique constraint and is skipped.
    Why `acks: all` matters: `acks` sets when the broker tells the producer the write succeeded. `acks=0` never waits (messages can vanish unnoticed), `acks=1` waits only for the partition leader (if the leader dies before followers copy the record, it is lost although the producer was told it succeeded), and `acks=all` waits until all in-sync replicas have it, so the record survives losing the leader. Two reasons it is required here: the outbox publisher (step 13e) calls `markPublished()` only after the ack, so the ack must mean the message is durable, otherwise a row could be marked published, the event lost, and nothing would ever retry it (the order would stay PENDING forever); and Kafka refuses to enable `enable.idempotence` without `acks=all`. It costs a little latency and works together with the topic's `min.insync.replicas`, which rejects writes when too few replicas are available. With `replicas(1)` on the local topic, `acks=all` behaves like `acks=1`, but set it now so the config stays correct on a multi-broker cluster (for example on AWS).
    How `KafkaAdmin` starts: you do not start it yourself. With `spring-kafka` on the classpath, Spring Boot's `KafkaAutoConfiguration` registers a `KafkaAdmin` bean built from `spring.kafka.*` (mainly `bootstrap-servers`). It implements `SmartInitializingSingleton`, so Spring calls it once all singleton beans exist, during application startup. It then collects every `NewTopic` bean (your `orders.events`), opens an `AdminClient` connection, checks which topics exist and creates the missing ones. If a topic exists with fewer partitions than the bean asks for it adds partitions, but it never deletes topics or reduces partitions. If Kafka is down, `fatalIfBrokerNotAvailable` is false by default, so it waits up to its operation timeout (about 30 s), logs a warning and lets the app finish starting. This happens only once, at startup: if Kafka comes up later nothing retries it, and the publisher would fail to send to a missing topic (unless the broker has `auto.create.topics.enable` on) until you restart the app.

- **`OutboxLagHigh`.** A Prometheus alert rule: `orderflow_outbox_lag_seconds > 60` for `2m`. The outbox lag is the age of the oldest outbox row that has not been published to Kafka yet (about 0 s normally, growing 1 s per second while Kafka is down). **Pending** means the condition is true but has not yet lasted the 2 minutes; **Firing** means it has been true for 2 minutes without a break. "+88 s" and "+208 s" are seconds after Kafka was stopped: the lag crossed 60 s at +63 s, Pending began at +88 s (the scrape and the rule evaluation each run every 15 s), Firing began 2 minutes later.
- **"All orders accounted for".** `scripts/drill_check.py` compares what clients were told with what the databases hold: the number of `201` responses equals the new rows in `orders`; all of them reached CONFIRMED (none PENDING); 0 unpublished outbox rows in either service; no order has duplicate events; the reserved stock per SKU equals the CONFIRMED quantities exactly. So every acknowledged order was delivered and processed exactly once.
- **"Failed" is not "lost", and neither means "committed but not published".** A *failed request* is one where the load tool got no 2xx answer; a status of `0` means the client's 10 s timeout or a broken connection. At 600 orders/s there were 21 of those; the slowest request took 10.03 s, which fits the timeout, so overload is the likely cause (it was not traced). Whether the server created an order for such a request is unknown to the client. *Lost* means an order the client got a `201` for that is missing from the database or stayed PENDING forever. *Committed but not published* is the outbox's job: those rows wait and are sent when Kafka returns, and "0 unpublished outbox rows" after draining shows none were left.
- **Why the order-service-kill drill's failed requests were never acknowledged.** The `201` is sent only after the order and its outbox row are committed. While the container was dead, nothing was listening, so new requests got "connection refused" and requests in flight when it was killed got a reset or no answer; none received a `201`. The check supports this: rows in `orders` equalled baseline plus the number of `201`s exactly (126,679 + 3,000 = 129,679), so none of the 600 failed requests left an order behind. That is one run; a kill landing between the commit and the response would leave an order without a `201`, and this run did not hit that window.

- **Virtual users, dropped iterations and the 500 ms line (steps 11b to 11d).** A VU is a k6 worker that runs one iteration (one order request) at a time; with the `constant-arrival-rate` executor k6 needs a free VU to start each scheduled iteration (script: 100 preallocated, 300 maximum). Run 2 sent 12,049 of 18,000 scheduled, so the server saw 397/s instead of 600/s. 500 ms is the script's own p95 pass line, hit in runs 2, 5 and 7; runs 1 and 8 had pressure (127 waiting requests, 53 and 232 dropped iterations) but passed. The script has no threshold on dropped iterations, so a short-delivered run can still pass (not fixed). Full explanation, including a correction of an earlier "stricter cut" remark: [perf.md](phase2/docs/perf.md), section "Reading the k6 numbers".
