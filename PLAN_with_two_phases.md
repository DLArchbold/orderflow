# PHASE 1: Postgres + Spring Boot API (Swagger) + React

You need: JDK 21, Maven, Node 22, and either Docker Desktop or a local PostgreSQL install.
Not in Phase 1: Kafka, Redis, security/login, Docker images, CI extras, Kubernetes, Terraform, AWS, load tests, most testing.

1. **Install the tools and start Postgres.**
   Do: run `docker compose -f infra/docker-compose.yml up -d` (or `make db`).
   No Docker? Install PostgreSQL, then create user `orderflow` (password `orderflow`) and a database named `orders`.
   Done when: you can connect to `localhost:5432`, database `orders`, user `orderflow` (psql, DBeaver or a VS Code extension).
2. **Start the backend skeleton.**
   Do: `cd services/order-service`, then `mvn spring-boot:run`.
   Done when: Swagger UI opens at http://localhost:8080/swagger-ui.html and lists 5 endpoints (they return 501 for now), `http://localhost:8080/actuator/health` says `UP`, and Postgres now has the tables `orders`, `order_lines` and `flyway_schema_history` (Flyway ran `V1__init.sql`).
3. **Read the domain code and run its test.**
   Do: read `domain/Order.java` and `domain/OrderStatus.java` (the order lifecycle), then run `mvn test`.
   The :: Method Reference operator can be replaced with a Lambda Expression  when passing in Executable functional interface as second argument when executing assertThrows. The tests in `OrderTest` are mainly to make sure order transitions by executing allowedNext() work as expected.
   Done when: the 6 tests in `OrderTest` pass and you can explain which status changes are allowed.
4. **Map the tables to Java (persistence).**
   Do: first add the migration `V2__order_lines_id.sql` (never edit `V1__init.sql`, Flyway has already applied it): drop the `order_lines` primary key, add `id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, and add `UNIQUE (order_id, line_no)`.
   Then create an `OrderEntity` for the `orders` table, an `OrderLineEntity` for the `order_lines` table (`@Id @GeneratedValue(strategy = IDENTITY) Long id`, `@ManyToOne(fetch = LAZY, optional = false) @JoinColumn(name = "order_id") OrderEntity order`, `lineNo`, `sku`, `quantity`), and a `JpaRepository<OrderEntity, UUID>`. Map the lines on the parent with `@OneToMany(mappedBy = "order", cascade = ALL, orphanRemoval = true)` and `@OrderBy("lineNo ASC")`, and add an `addLine(sku, quantity)` helper that sets both sides and `lineNo`. Store `status` as a string (`@Enumerated(EnumType.STRING)`). Let the entity's `confirm()` / `cancel()` methods reuse the rules in `OrderStatus`.
   Watch for: the list endpoint loading lines one order at a time (N+1); fix it with `@EntityGraph(attributePaths = "lines")`.
   Done when: the app still starts (`ddl-auto: validate` means any mismatch with the tables is reported at startup).
5. **Implement the endpoints, one at a time, in `OrderController`.**
   Order: create, list, get one, confirm, cancel.
   Rules: create returns 201 and status `PENDING`; unknown id returns 404; a not-allowed status change returns 409; invalid input returns 400 (the `@Valid` rules are already in the request record). Add one `@RestControllerAdvice` class so errors come back as small JSON messages.
   Done when: every endpoint works from Swagger UI ("Try it out"), and you can see the rows change in Postgres.
6. **Polish the Swagger docs.**
   Do: add `@Operation(description = ...)`, `@ApiResponse` codes and `@Schema(example = ...)` values on the request/response records.
   Done when: someone else could use the whole API from Swagger UI alone. (Swagger UI is generated by springdoc from your code; the raw JSON is at `/v3/api-docs`.)
7. **Start the React app.**
   Do: `cd frontend`, `npm install`, `npm run dev`.
   Done when: http://localhost:5173 loads, shows the form and an empty list, and no red error line appears (the backend must be running).
8. **Create orders from the UI.**
   The form and API calls are already written in `src/App.tsx` and `src/api.ts`.
   Done when: a new order appears in the list and in Postgres. Read both files and make one change of your own (for example a second order line, or a customer filter).
9. **Confirm and cancel from the UI, with errors.**
   Done when: the buttons change the status, and a not-allowed change (cancel an order you already cancelled via Swagger, then refresh) shows the 409 message in the UI.
10. **Wrap up Phase 1.**
    Do: fill in the README with run steps and two screenshots (Swagger UI and the app), commit, push to GitHub.
    Done when: the GitHub CI check (backend `mvn package`, frontend `npm run build`) is green and a stranger could follow the README to run it.

# PHASE 2: the rest (do in this order, after Phase 1 works)

Read `phase2/README.md` first: it says what each folder is and when to bring it back.
**Test-first rule (steps 12 to 16):** commit the failing test before the implementation. Only claim test-driven development if you really worked that way.

11. **Full local stack.** Use `phase2/infra/docker-compose.full.yml` (Postgres, Kafka, Redis, Jaeger, Prometheus, Grafana). Move `phase2/inventory-service` to `services/inventory-service`, and add `CREATE DATABASE inventory;` to `infra/postgres-init/01-create-dbs.sql`.
    Done when: all containers start.
12. **Outbox write.** Copy `phase2/order-service/V2__idempotency_and_outbox.sql` into the migrations folder, renamed to `V3__idempotency_and_outbox.sql` (`V2` is taken by the `order_lines` id migration from step 4), bring back the outbox classes from `phase2/order-service/src-additions/outbox`, add the Kafka dependency from `pom-additions.xml`, and make order creation insert an outbox row in the same transaction.
    Done when: a Testcontainers (PostgreSQL) test proves that on rollback neither the order nor the outbox row exists.
13. **Outbox publisher.** Implement `OutboxPublisher` (send, wait for ack, mark published).
    Done when: a Kafka Testcontainers test shows an event arrives once the order commits, and unpublished rows are retried after Kafka was down.
14. **Inventory consumer.** Idempotent processing: `processed_messages` insert + stock reservation + result event in one transaction.
    Done when: delivering the same message twice reserves stock only once (test), and stock never goes negative.
15. **Close the loop.** Order-service consumes the inventory result and moves the order to CONFIRMED or REJECTED (this replaces the manual `/confirm` endpoint).
    Done when: an end-to-end test (two services, real Kafka and Postgres) takes an order from PENDING to CONFIRMED, and to REJECTED when stock is insufficient.
16. **Failure handling.** Consumer retries with backoff and a dead-letter topic, plus a way to replay dead letters.
    Done when: a poison message lands in the DLT without blocking the partition, and replaying it after a fix succeeds.
17. **Resilience and caching.** Add one synchronous call (order-service asks inventory-service for stock availability), wrapped with a Resilience4j timeout, circuit breaker and bulkhead, with a fallback. Cache that read in Redis.
    Done when: with inventory-service stopped you see the breaker open, the fallback response, and recovery after restart; a repeated read is served from Redis.
18. **Security.** OAuth2/JWT resource server (`phase2/order-service/src-additions/config/SecurityConfig.java`; Keycloak in compose or another OIDC provider), roles, customers see only their own orders, CORS for the frontend. Fill in `phase2/docs/security.md`.
    Done when: tests show 401 without a token, 403 for another customer's order, 200 for your own.
19. **Database tuning.** Seed a few million order rows, find your slowest realistic query, run `EXPLAIN ANALYZE`, add or change an index.
    Done when: before/after plans and timings are recorded in `phase2/docs/perf.md`.
20. **Frontend extras and tests.** Add live status via SSE (endpoint in order-service, hook in `phase2/frontend/hooks`), React Testing Library tests, and a Playwright test of the main flow.
    Done when: you can watch an order change status without refreshing, and the tests pass.
21. **Observability.** Actuator health/readiness, Micrometer metrics (orders created, outbox lag, DLT count) scraped by Prometheus, a Grafana dashboard, one alert rule, OpenTelemetry traces in Jaeger across both services, a correlation id in logs and Kafka headers.
    Done when: you can follow one order through a single trace, and the alert fires when you stop the publisher.
22. **CI/CD and scanning.** Move `phase2/github/*` into `.github/`; build and push Docker images, run the integration tests; keep CodeQL and Dependabot on; fix real findings and log each one in `security.md`.
    Done when: a push to main produces tested images with a green pipeline.
23. **Kubernetes (light).** Finish the manifests in `phase2/infra/k8s`; CI creates a `kind` cluster, applies them and waits for readiness.
    Done when: CI shows both services Ready on kind.
24. **AWS with Terraform.** Build `phase2/infra/terraform` step by step (network, ECR, RDS, Kafka option, ECS Fargate behind an ALB with rolling deployment, secrets); see `phase2/infra/aws/README.md`.
    Done when: the app runs at a public URL and a deploy was done while k6 traffic ran with zero failed requests (keep the output). Then `terraform destroy`.
25. **Load test.** Run `phase2/load-tests/k6/create-orders.js` (adjust it to your final API).
    Done when: `perf.md` records throughput, p95 latency and error rate with the exact setup.
26. **Destructive resiliency drill.** Kill inventory-service and Kafka in turn while traffic runs; restart them.
    Done when: no orders are lost or duplicated (count orders vs processed events) and you wrote down what you saw.
27. **Documentation.** Fill in the README results table from steps 19, 24, 25, 26; add architecture diagram and ADRs for decisions you actually made; add a short demo GIF.
    Done when: a stranger can clone, run the full stack and see the demo work.
28. **Resume.** Use the longer OrderFlow entry only now, with numbers from your own measurements; keep the wording identical across all versions.
    Done when: every claim maps to a README results row, `security.md`, or a test.
